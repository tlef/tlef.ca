When developing a distributed sharded system you cannot simply rely on the standard auto-increment process for record ids without the overhead of database coordination.

1. Your new PKs need to be guarenteed unique without authoritaive coordination.

Are you using a form of SQL for you data? In almost all cases, SQL injections happen in PK order (least to greatest), and appending to the end of the table is way more efficeint then injecting into the middle

2. Your new PKs need to be "greater" than any of the previous PKs.

## Unique, sequential Ids

When inserting data into a SQL database your PKss need to be two things: Unique and Sequential. Unique for obvious reasons, but with SQL, the order of records in the table is dictated by the interation order of the PKs, and it's also most efficient to insert at the end of the table record. This means that the most efficient PK strategy is sequential values.
This is how the built in "auto-incremennt PK" mechanisims work, and they can do this because they know the vlaue of the latest PK generated and can just auto-increment.

So what do you do if you have a distributed system for parrallel efficiency? Who's keeping track of the value of the latest PK generated? As soon as you start recording this, you've recreated the bottleneck that you setout to solve.

Enter [Snowflake Ids](https://en.wikipedia.org/wiki/Snowflake_ID). An idea that Twitter came up with to generate system-wide unique, and sequential Ids for this exact purpose.

You can read up on the details in the link above, but the short of it is that it's a 64 bit integer that is generated by a timestamp, machine-id, and per-machine sequence value. This means that given a unique machine-id within your system, without coordination, each machine can generate a new sequential number that will be unique among all of your machines.

This is exactly what we need.

## Encoding

So now you have an ugly 64-bit integer you need to pass around. What if we then encoded it. That could shrink the size (looks better in a URL), but there's one other trick we can do. What if we also encoded it with a prefix to identify what kind of Id is it.
Is it a `userId`? Lets start it with `Us`. Is it a `widgetId`? Lets start it with `Wi`.

```
7389802228174819330 -> Us52ebYKNr44q61PaB
7389802228174819332 -> Wi9xQyOMYQ11JewQwx
```

You can now see these "random" ids, and you know what they represent. This isn't anything revolutionary, just a handy step to make your life in development and support a little easier.
